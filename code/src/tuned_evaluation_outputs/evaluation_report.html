    §1Executive summary

    Re-run end-to-end on the tuned checkpoints (baseline job 716641, comparative job 717089) and, for the first time, a genuinely validation-tuned refinement threshold (0.5). The headline: the two models are now close on raw overlap, calibration still passes with a genuine, verified signal, and one clear, specific regression — comparative's eCSF topology — stands out for follow-up.

    Segmentation

    Baseline and comparative are now a near-tie on raw overlap — mean foreground Dice 0.780 vs. 0.781, down from a 0.046 gap in the earlier (untuned-checkpoint) run. But one clear regression remains: comparative's eCSF Euler characteristic difference is 4.4× baseline's (253.7 vs. 57.7 — roughly 196 more topological defects per case on average), despite eCSF Dice being nearly identical (0.700 vs. 0.708). See §4–5.

    Calibration

    Passes, with a real and verified signal (Spearman ρ = 0.417, p ≈ 0, n = 16.8M voxels) — but still not from the model's own uncertainty head. That head's weights remain statistically indistinguishable from a fresh random init even though both previously-identified structural bugs are now fixed in this checkpoint's training config (nonzero uncertainty_loss_weight, self.mc_dropout wired into forward()). The evaluation script substitutes softmax predictive entropy instead. See §6.

    Data

    Three test cases (sub-017, sub-020, sub-025) still collapse on eCSF/GM — Dice as low as 0.12–0.49 there, vs. 0.78–0.90 on a typical case — but less totally than before: the earlier run's exact-zero Brainstem collapse is gone (worst case now 0.14, on sub-017). Reproducible across both newly, independently-retrained checkpoints. See §8.

    §2How the evaluation pipeline works

    src/evaluation/full_evaluation.py is a single consolidated script (merged from six earlier modules) built around one idea: it never imports a concrete model class. Instead it defines a structural typing.Protocol — SegmentationModel for the baseline, UncertaintyModel for the comparative model — and both real checkpoints are wrapped in a thin adapter that satisfies it. That's what let this evaluation code be written, tested, and verified before either real checkpoint existed, and run unmodified once they did.

    Model correctness checks, before trusting any number

    Before running the real evaluation, both checkpoints were verified directly, not assumed:

    • Strict weight loading — load_state_dict(..., strict=True) for both BaselineUNet (22.6M params) and UncertaintyUNet (22.6M + a small uncertainty head): all keys matched exactly.
    • Non-degeneracy check — both models predict all 8 real tissue classes with sensible voxel counts on real in-distribution data (not the single-class collapse seen when the baseline checkpoint was earlier fed out-of-distribution synthetic data as a sanity test).
    • Cross-model agreement — baseline and comparative agree with each other on 96.0% of voxels on a sample patch, and each agrees with ground truth on ~90%, consistent with two independently-trained models sharing the same task and backbone.

    Speed: what actually helped

    This ran on a 4-core CPU laptop, no GPU — full 128³ sliding-window inference for both models across 12 cases is fundamentally compute-bound. Before touching the script, I benchmarked four candidate speedups; only one helped:

    LeverResultUsed?
    Batching multiple tiles per forward call44.6s/patch vs. 15.1s/patch looped — slowerNo
    Thread count 4 → 8 (this CPU has 4 physical cores)14.0s vs. 14.3s — no changeNo
    Conv+BatchNorm fusion (mathematically exact in eval mode)16.35s vs. 16.46s — no changeNo
    Tile stride 50%→100% overlap (full coverage either way)129 → 88 tiles across the 12 casesYes

    The reason: a volume between 1×–2× the patch size needs exactly 2 tiles per axis regardless of stride — overlap there is unavoidable. But several test cases (e.g. sub-054 at 204×247×195) needed 3 tiles per axis under 50% overlap; raising the stride to 100% (no intentional overlap, full voxel coverage unchanged) cut that back down to 2 per axis. Net effect (same lever, same code path as the earlier run): this run finished in 30.2 minutes — noticeably faster than the earlier 47.0-minute run on the same hardware, most likely system load variance between sessions rather than any code change.

    §3What's being measured

    MetricWhat it answersComputed by
    DiceOf the voxels a class should occupy, how many did the model get right? (0–1, higher better)dice_per_class, mean_dice
    Euler char. diff. (ED)How many extra/missing holes or disconnected blobs does the prediction have vs. ground truth? Catches anatomically implausible shapes Dice can miss.euler_characteristic_difference
    Calibration (Spearman ρ)Does the model's predicted uncertainty actually track where it's wrong? Gate: ρ>0.2 and p<0.05.compute_calibration_summary
    Refinement Δ (Dice/ED)Does the rule-based, uncertainty-guided boundary refinement step actually improve eCSF/GM/dGM?compare_before_after_refinement

    Mean Dice excludes background (class 0) by default — it dominates volume and is trivially easy, so folding it in would mask the foreground performance this evaluation actually cares about. ED uses 6-connectivity, applied identically to prediction and ground truth.

    §6Calibration — does predicted uncertainty track real error?

    This is the load-bearing check for the whole research option: if uncertainty doesn't correlate with real error, the refinement step in §7 has nothing real to act on. It passes — Spearman ρ = 0.417 (p ≈ 0, n = 16,832,053 voxels), comfortably past the ρ>0.2, p<0.05 gate.

    But

    That signal still isn't coming from UncertaintyUNet's own dedicated uncertainty head — even though both structural bugs the earlier report flagged are now fixed in this checkpoint's training setup. I re-verified directly rather than assuming either was still broken:

    1. Both known bugs are fixed, and it still didn't help. training/train_config_comparative.yaml now sets uncertainty_loss_weight: 0.1 (nonzero — it was 0.0 before), and UncertaintyUNet.forward() now calls self.mc_dropout(x) before both heads (it didn't before). Despite that, the head's weights are still statistically indistinguishable from a fresh random init: std 0.096, vs. 0.100 for an untrained network — compare the segmentation head, which moved from a fresh-init std of 0.106 to a trained 0.150.

    Measured directly on 2 held-out case(s): the raw uncertainty head's own output correlates with real voxel error at ρ = 0.144 (p = 0) — a real but weak signal on its own, well below the ρ>0.2 gate the substitute clears. The evaluation script's fallback — plain single-pass softmax predictive entropy — is what §6's headline ρ = 0.417 above actually measures.

    Fixing the two identified bugs wasn't enough on its own; something else is still preventing this head from learning a useful signal — worth instrumenting its gradient norm directly during a future training run.

    §7Before/after refinement — eCSF, GM, dGM

    Given calibration passes, and now with a genuinely validation-tuned threshold, does the rule-based refinement step (reassign high-uncertainty boundary voxels to their local-majority class) actually help? Dice barely moves, but eCSF's topology improves substantially. That split makes sense: refinement only reassigns boundary voxels that were already close to a class boundary, so it was never going to move overlap much — but it can and does clean up small disconnected fragments.

    Now tuned

    Unlike the earlier run, refinement_threshold = 0.5 here is role 4's actual validation-selected value, not a placeholder — a sweep over {0.3, 0.4, 0.5, 0.6, 0.7} on the validation split picked 0.5 as maximizing target-class Dice (0.7649 vs. 0.7641 with no refinement at all; see training/training_results/comparative_run_1(anthony)/tuning_results/refinement_threshold_sweep.json). Dice staying flat at test time is therefore a real result, not an artifact of an untuned threshold — refinement's benefit here is topological (eCSF's ED drop above), not overlap-based.

    §8Three cases collapse on both models

    sub-017, sub-020, and sub-025 still score dramatically worse than every other test case on eCSF and GM — on both independently-retrained checkpoints — though less totally than in the earlier run: Cerebellum and Brainstem are no longer near-zero (comparative's worst Brainstem score is now 0.14, on sub-017, not 0.000).

It reproduces across two newly, independently-retrained checkpoints — not just the earlier pair — which strengthens the case that this is a genuine property of these three volumes (very early gestational age? a preprocessing edge case?) rather than a training artifact — still worth a direct look at the source volumes before trusting the pooled per-class means at face value.
